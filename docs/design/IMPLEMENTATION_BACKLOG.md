- [x] crates.io freshness provider — `research/providers/crates_io.py::CratesIoUpdateProvider` (`ComponentUpdateProvider` for the `cargo` ecosystem, same shape as `PyPIUpdateProvider`/`NpmUpdateProvider`). Response shape (`crate.max_stable_version`, the top-level `versions` list for release date/yanked status) verified live against the real API (`GET /api/v1/crates/serde`). Cargo's own bare-version convention (`serde = "1.0"` means `^1.0`, a caret range, unlike npm's bare-is-exact convention) is handled explicitly in `analysis/update_intelligence.py::build_current_state` (`_BARE_CONSTRAINT_IS_EXACT_PIN`) so a Cargo dependency is only ever treated as an exact current-version pin when explicitly written with `=` — never guessed from the bare form. `proposals/engine.py::change_plan_for_component_update` now also covers Cargo's *simple string form* (`name = "=1.0.219"`) via a raw-text regex substitution — the same discipline already used for pyproject.toml/package.json, not a full TOML parse/re-serialize (which would reformat the whole file). Cargo's *table* form (`name = { version = "=1.0.219", features = [...] }`) is deliberately never rewritten -- a nested `version` key isn't a name-adjacent literal a regex could safely, unambiguously locate -- so a table-form Cargo update still falls through to the external-implementer handoff, never a guessed patch
- [x] Go module proxy freshness provider — `research/providers/go_proxy.py::GoProxyUpdateProvider` (`ComponentUpdateProvider` for the `go` ecosystem, against `proxy.golang.org/<module>/@latest`, the same proxy `go get` itself uses). The proxy's module-path escaping rule (every uppercase letter becomes `!<lowercase letter>`) verified live against a real mixed-case module (`github.com/Masterminds/semver` → `github.com/!masterminds/semver`). Go's own `go.mod` convention is the opposite of Cargo's: every `require` line is already an exact, Minimal-Version-Selection-resolved version (or a pseudo-version), always `v`-prefixed and never a range, so `_EXACT_PIN_RE` gained an optional `v` prefix and `go` was added to `_BARE_CONSTRAINT_IS_EXACT_PIN` — without both, every Go dependency's current version would silently stay unresolved forever (the version string "v1.2.3" starts with "v", not a digit, so the pre-existing regex would never match it at all)
- [x] Maven Central freshness provider — `research/providers/maven_central.py::MavenCentralUpdateProvider` (`ComponentUpdateProvider` for the `maven` ecosystem, against `repo1.maven.org/maven2/<group-path>/<artifactId>/maven-metadata.xml` — the same metadata file Maven itself consults to resolve `RELEASE`/`LATEST` placeholders). Uses `<versioning><release>` (falling back to `<latest>` when `<release>` is absent) rather than the Maven Central Search API's own default sort order, because some coordinates publish more than one version *flavor* under the identical groupId:artifactId (Guava's `-jre`/`-android` builds, published independently and interleaved in time) — `<release>` is Maven Central's own authoritative pointer and resolves that ambiguity without this provider having to guess from a sorted list, verified live against `com.google.guava:guava`'s real metadata (`<release>33.7.1-jre</release>`). Maven's own pom.xml convention is like Go's, not Cargo's: a literal `<version>1.2.3</version>` (the only form `analysis/dependencies.py::_extract_pom_dependencies` ever extracts — a `${property}`-templated one is always skipped) means exactly that version, so `maven` was added to `_BARE_CONSTRAINT_IS_EXACT_PIN`; Maven's own range syntax (`[1.0,2.0)`, `(,2.0]`) starts with a bracket/paren character `_EXACT_PIN_RE` does not match, so it is correctly excluded with no Maven-specific range parser needed. End-to-end live-validated (`si check-updates --check-vulnerabilities` against a real pom.xml): `org.apache.logging.log4j:log4j-core@2.14.1` correctly resolves to available `3.0.0-beta3` with its real known advisories, and `com.google.guava:guava@30.0-jre` correctly resolves to available `33.7.1-jre`
- [x] `si dashboard --check-updates`/`si check-updates` own `--help`/docstring text still said "pypi/npm/cargo/go" in four places (`cli/main.py`'s `_DASHBOARD_CHECK_UPDATES_OPTION` help, `_CHECK_UPDATES_VULNERABILITIES_OPTION` help, and `check_updates()`'s own docstring, twice) even though `_update_providers()`/`_vulnerability_providers()` had already registered a `maven` entry each since the Maven Central provider above landed — confirmed via `git log` that PR only updated the `dashboard()` command's own docstring (which already correctly said "pypi/npm/cargo/go/maven") and missed these four sibling occurrences, the same "producer changed, consumer text didn't" drift pattern as the earlier `--plan-out` fix above, just a different, previously-unexploited set of lines in the same file.
